# V8.1 Driving performance and road reliability

Scope: profile the driving frame stalls, fix the confirmed cause, investigate the road corridor limits of V8 and
V8.0.1, check vehicle and camera stability. No gameplay, vehicle, landmark, rendering-mode or visual changes.

Status: implemented and measured; not committed.

Machine for every number below: Intel UHD Graphics (ANGLE / Direct3D 11), Edge, 1920 x 1080, medium preset,
adaptive resolution off, production build served by `vite preview`. Baseline = commit `dbefe4c` (V8.0.1), built and
measured in the same session as V8.1. Raw data: `docs/perf-v8.1.json`.

## 1. Root cause of the 1-2.5 s stalls

**First-use shader compilation of the V7 Jalan China street section.**

three.js compiles a material's shader program on the first frame an object using it is drawn, synchronously on the
main thread. The V7 section uses about 40 distinct `MeshStandardMaterial` program variants (photographic road,
facades, glass, car paint). On this GPU each one takes 150-300 ms to compile. The section is never distance-culled,
so it is drawn as soon as it is inside the camera's 2,000 m far plane and frustum. When it had not been drawn before,
the first frames that saw it compiled 1-7 programs each.

Evidence (per-frame attribution in `tools/dev/drive-bench.ts`):

- Cold high-speed run (start, then straight to the Jalan Tun Abang Haji Openg route, as the e2e high-speed test
  does), 3 runs: worst frames 1,112 ms, 2,047 ms and 2,611 ms; 12-16 frames over 200 ms per run. Every frame over
  200 ms compiled new programs (`renderer.info.programs` grew), all `physical/STANDARD` variants, and all in one
  7 s window with the car at (-334, 1250), 1.3 km from Jalan China, driving toward it. The program count went from
  50 to 93 during the run.
- A probe of the scene at that spot found no standard-material object nearby: the only ones were the V7 section
  (55 meshes) and the drivable car.
- A normal start has the same cost, paid during play instead: the first 360-degree look round at the spawn froze
  for 2.75-2.83 s (3 runs).
- The same route driven after the section had been seen (warm) never exceeded 60 ms.
- The earlier 1-2.5 s reports came from the e2e high-speed test, which teleports to that route right after start.
  It is not a dev-server effect: the same stalls reproduce on the production build.

Ruled out by measurement:

| Candidate | Finding |
|---|---|
| Garbage collection | Chrome trace of a cold Jalan China drive: largest major GC 5.7 ms, largest minor GC 4.2 ms. |
| Chunk fetch / JSON parse | Chunk files are 13-30 KB; parse under 1.5 ms per frame at worst. |
| Collision updates | `addChunk` / `removeChunk` under 1.1 ms per frame at worst. |
| Chunk mesh builds | Median 3-5 ms, worst single build 35-48 ms. A visible hitch, never a stall (section 7). |
| Vehicle physics | 0.1-0.6 ms per frame. |
| Chase camera | 0.06-0.2 ms per frame. |
| Minimap, landmark-model streaming bookkeeping | Under 0.2 ms per frame. |

Secondary findings:

- A streamed landmark model (St. Joseph's Cathedral area, (-316, 794)) compiled one more program on its first
  frame: 126-177 ms.
- The V7 section's first draw also uploaded 1-2 textures and its geometry: 75-300 ms.
- One `MeshBasicMaterial` variant compiles on a chunk's warm-up draw once per session: 110-150 ms.
- In the V7 Jalan China lane the frame rate is limited by the GPU, not by stalls: render takes 9 ms of CPU, frames
  take 18-21 ms. In one cold baseline run the frame rate there fell to 44 fps with 27 frames over 50 ms, all inside
  `renderer.render` with no new program, geometry or texture. A repeat cold run showed 1 such frame. This is
  run-to-run GPU variance on this machine, not a code path.

## 2. Optimizations

1. **Prepare before drawing** (`src/world/prepareDraw.ts`, new): uploads an object's textures (material maps and
   shader-uniform textures) and starts compiling its programs with `renderer.compile`. It does not draw the object.
   three.js does not query a program's link status until first use, so the work runs in the GPU process
   (`KHR_parallel_shader_compile`). Programs are compiled for the render target the object will really be drawn
   into, so the variants match exactly.
2. **V7 section** (`src/v5/controller.ts`, `src/v5/pipeline.ts`): `setMode` prepares the section right after
   building it and enabling the pipeline (`V5Pipeline.prepare`, which uses the composer's target when ambient
   occlusion is on). At start-up this happens behind the existing "Preparing the Jalan China street section…" step.
3. **Landmark models** (`src/world/landmarks/LandmarkModels.ts`, `src/main.ts`): a streamed model joins the scene
   only once its programs report ready. The old LOD stays up meanwhile, as before, so no hole appears.

Tried and reverted: the same prepare step in `ChunkManager.build`. The chunk's warm-up draw comes in the same
frame, which forces the compile anyway, so it showed no gain.

No change to chunk streaming, collision, physics, camera or rendering.

## 4. Road corridor investigation

`tools/dev/corridor-probe.ts` samples the mapped centre lines of the tested routes every 2 m in the default V7
rendering. At each sample it measures, across the road, where the surface is really free: no building outline, no
five-foot-way pier, no parked car. It changes nothing.

| Street (block loop) | Centre line blocked | Free corridor | Its middle vs the OSM line |
|---|---|---|---|
| Jalan China | 22 of 55 samples | 2.5-2.75 m (the lane between the parked rows) | 2.25 m (median) |
| Jalan Carpenter | 0 of 56 | at least 7 m | median 1.4 m |
| Jalan Bishopgate | 0 of 40 | at least 5.75 m | median 1.0 m |
| Jalan Main Bazaar | 0 of 44 | at least 4 m (open on the river side) | median 5.1 m |
| Jalan Tun Abang Haji Openg (2.2 km) | 0 of 1,127 | at least 20 m | median 0 m |

Findings:

1. **Jalan China centre-line offset.** Confirmed and quantified: the OSM line runs through the east parked row. The
   real drivable surface is the 2.5-2.75 m lane, whose middle is 2.25 m from the line. The runtime "on the road"
   rule (half the mapped 6 m width plus 1 m) still covers the whole lane, so the HUD and off-road drag are correct
   there. No defect was demonstrated, and no change was made.
2. **Narrow lane between parked cars.** It is the street's real width, and it is drivable end to end. Four probe
   samples reading 0.25-0.5 m were the probe finding the gap between two east-row bumpers near the line, not a
   narrowing of the lane.
3. **Jalan Carpenter junction.** The centre line is clear with at least 7 m free across the street. The tight spot
   is the turning path past the Jalan China east-block corner, which the tested route takes from the lane in the
   junction. Nothing in the data supports moving the line.
4. **Pedestrian bridges.** The only decks on the tested routes are three footway decks on Jalan Tun Abang Haji Openg,
   0-0.07 m above the ground. They are correctly ordinary ground for the car (V8 rule: decks under 0.35 m on dry
   land). No raised footbridge crosses a tested route; raised footways and piers stay refused by the deck rule
   (unit-tested).
5. **Elevation.** Steepest grade on the block loop is 11.2 % (Jalan Bishopgate near (266, 47)), and 10.6 % in Jalan
   China. Jalan Tun Abang Haji Openg is at most 6.2 %. Driven runs: maximum gap between car and ground 0.09-0.13 m;
   pitch and roll within the existing test limits.

**Uncertainty, documented instead of implemented.** A drivable-corridor layer is only needed for Jalan China.
There, the true corridor comes from the V7 section's own data (the mapped frontages plus the V7 parked rows), not
from OSM. One untested consequence: the R reset-to-road candidates lie on the OSM line, which is occupied by parked
cars there. R falls back to the last pose stored on the road, and that is only stored within 2.48 m of the line;
the lane middle is 2.25 m from it. R in the lane was not exercised in this phase.

## 5. Vehicle and camera stability

- **Physics** is already sub-stepped (steps of at most 1/120 s), and `main.ts` caps a frame at 0.1 s. A stall
  therefore slows game time instead of moving the car further, so there is no catch-up spiral.
- New unit test: the same driving at 30 and 60 fps ends at the same point as at 144 fps (within 0.15 m over 60 m).
  The same holds with a 100 ms stall every 30th frame (within 0.6 m; frame boundaries then shift control timing).
  At full throttle into a wall with every frame a 100 ms stall, the car does not tunnel and rests at the wall.
  Measured spread across 30-240 fps: 8 cm and 0.005 rad.
- A fixed-step accumulator with render interpolation was therefore not added: no defect was demonstrated.
- **Chase camera** uses exponential smoothing scaled by dt, so it is frame-rate independent. No jitter or snapping
  was seen in the measurements. The car's maximum height error was 0.13 m. No change.
- During a long stall (before this fix), the car moved at most 0.1 s of travel per frame, and no collision or
  unbuilt-chunk frame occurred in any run.

- Unit: 65 of 65 pass (64 earlier plus the frame-rate test). `tsc` is clean. `vite build` is OK.
- Focused e2e with `PUBLIC_PORT=5174`: driving, OP mode, landmarks, gameplay (walking and running, shop
  interactions), district (five-foot way), and production (static build for Cloudflare). **27 of 31 pass.**
  - Driving, all 9 pass: default V7 start, enter and exit, the lane, Drive Car, the block loop in V7 and in V4,
    collisions with walls, parked cars and the river, switching to OP mode, and the high-speed streaming run.
  - The high-speed e2e run now reports a worst frame of 98 ms at 58.8 fps. In the V8.0.1 report, single stalls of
    1-2.5 s occurred on this run.
  - OP mode 3 of 3, gameplay 8 of 8, district 4 of 4, production 2 of 2, landmarks 1 of 5.
  - **The 4 landmark-model failures pre-date V8.1.** The same 4 tests fail the same way on the unchanged V8.0.1
    source, which was checked by stashing the V8.1 changes and rerunning. They expect every registered landmark
    model to load at the spawn. Since the V8 UI cleanup the game starts in V7, which hides the three temple-area
    models (the section draws its own versions). Left unchanged, for your decision: the tests should not simply be
    switched to V4 to pass.

## 7. Remaining limitations

- **Chunk builds at driving speed.** A heavy old-town chunk builds in 35-48 ms in one frame, and two builds can share
  a frame. With GPU time on top, this gives 50-80 ms frames during high-speed driving: 0-12 per 2 km run, varying
  between runs of the same build. Not addressed in this phase.
- **First-draw geometry and texture uploads** of the V7 section remain: 75-120 ms frames once, after the first
  look.
- **One-off chunk material variants** (`MeshBasicMaterial`, depth) still compile on first use: 40-150 ms, once per
  session.
- **GPU limit in the V7 lane on integrated graphics.** About 45-54 fps there, with intermittent 50-160 ms frames
  inside the render call. Rendering changes are out of scope.
- These are measurements on one machine. They do not prove a stall cannot occur elsewhere.

## 9. Recommendation for V8.2

1. **Split heavy chunk builds across frames.** Terrain and roads in one frame, buildings in another, as decoration
   already is. Paint the ground canvas texture off the main thread (OffscreenCanvas). This targets the remaining
   50-80 ms build frames at speed. Measure with `drive-bench.ts --scenarios=D`.
2. **Jalan China corridor from the V7 data.** Give the reset key (and the test driver) the V7 lane as the drivable
   corridor for Jalan China, after first adding an e2e test of R in the lane to confirm the risk in section 4.
3. **Fewer program variants in the V7 section.** Sharing material permutations would cut first-load compile time and
   GPU cost on integrated graphics. This is a rendering change, so it needs its own approval.
