# V8.5 Mobile driving

Scope: make the V8.4 driving and GPS navigation usable on phone and tablet browsers. The world, vehicle physics,
routing engine, OSM data, shader preparation (V8.1) and chunk scheduling (V8.2) are unchanged. No new assets.

Status: implemented and tested locally. **Not committed, pushed or deployed.**

## 1. Touch driving controls (Task 1)

At the wheel on a touch device the walking joystick and RUN / JUMP buttons are replaced by:

| Control | Where | Action |
| --- | --- | --- |
| Steering pad | bottom left | analogue: finger position left / right of centre (full lock at 70 % of the half-width, small dead zone); slide to change |
| GAS | bottom right | throttle while held |
| BRAKE / REVERSE | left of GAS | brake while held; keeps going into reverse once stopped (same as S) |
| HANDBRAKE | above BRAKE | handbrake while held (same as Space) |
| EXIT | above the steering pad | get out (dimmed while moving; tapping then says "Stop the car before getting out") |
| CAM | beside EXIT | steps the chase-camera distance (same as V); pinch on the 3D view sets any distance |
| RESET | above CAM | safe road reset (same as R) |
| GPS | beside RESET | opens the destination list |
| Drag on the 3D view | anywhere else | rotates the chase camera |

On foot, "Enter Car" is a tap button above the joystick.

Implementation (`src/ui/MobileControls.ts`): the touch layer writes the same `Input` fields the keyboard path uses
(`touchX` → steer, `touchY` → throttle, new `touchHandbrake`), and the one-shot buttons call the existing key actions
through the new `Input.trigger(action)`. There is no separate mobile physics. Each held control is tracked by its
touch identifier, so steering + gas + handbrake work together. Brake beats gas when both are held.

Every held control is released when:
- a finger lifts, or its touch is cancelled;
- the window loses focus, the page is hidden or unloaded (`pagehide`), or the orientation changes;
- gameplay input is switched off (pause, settings, full map, place panel);
- the player gets in or out of the car.

Every touch event also drops held controls whose finger is no longer on the screen, to catch a missed `touchend`.
Taps on the GPS button, the GPS list and the next-turn hint use their own touch identifiers, so they work while
another finger holds a pedal and never reach the pedals or the camera.

## 2. Responsive HUD (Tasks 2 and 3)

`body.touch` / `body.touch-drive` scope all layout changes; desktop CSS is unchanged except one fix (below).

- **Portrait:** the steering pad and the 2 × 2 GPS / RESET / EXIT / CAM block sit on the left; GAS, BRAKE and
  HANDBRAKE on the right, with the speedometer (gear + km/h) above them. The minimap is at the top right and the
  next-turn hint (instruction + remaining distance + ✕ cancel) at the top left. The OSM / Overture credit stays on the
  bottom edge, below the controls. The GPS list opens above the left block and never covers a control.
- **Landscape phones:** the top-bar buttons and the minimap zoom buttons form rows beside the minimap, the speedometer
  moves to the bottom centre, and the GPS list opens in the middle (it can cover the place name and hint while open).
- Toasts wrap instead of running off narrow screens. On small touch screens the "Loading area…" note sits below the
  right-hand buttons instead of over the place name.
- **Fix that also applies to desktop:** at window widths of 721–1100 px (tablets, narrow desktop windows), the
  next-turn hint used to overlap the place name. It now sits below it.

GPS without a keyboard: GPS → pick Lau Ya Keng (or any reachable destination) → follow the magenta route and the
hint → cancel with the hint's ✕ or the list's "Cancel navigation". Routing is untouched, so one-way and
pedestrian-only rules are exactly V8.4's (the V8.4 router unit tests and `gps.spec` still pass).

## 3. Tests (Task 5)

New `tests/e2e/touch-drive.spec.ts` (mobile-390 and mobile-360 projects, Chromium touch emulation with CDP touch
events) checks:

1. The Enter Car tap button does not overlap the joystick, and tapping it gets in.
2. Two fingers at once: steering right + GAS both reach `Input`, and the wheel angle moves. Sliding the steering
   finger steers left. Lifting the steering finger keeps GAS held. The car moves more than 8 km/h without touching
   a building.
3. GAS + BRAKE gives braking, never throttle. Holding BRAKE stops the car and engages reverse (gear R).
4. HANDBRAKE is on only while held.
5. Nothing stays held after touch cancel, window blur, orientation change, pagehide, the pause menu, a finger
   sliding off its button, or a finger whose lift the page never received.
6. CAM changes the chase distance, a drag rotates the camera, and RESET runs the safe reset.
7. GPS by touch: open the list while another finger holds BRAKE (the brake stays held), pick Lau Ya Keng, and the
   pedals stay idle. Driving with GAS makes the hint count down (e.g. "91 m: Turn left onto Jalan Carpenter |
   680 m" → "81 m … | 670 m").
8. Layout sweep at 360×800, 390×844, 430×932, 768×1024, 800×360, 844×390 and 932×430: every HUD element is inside
   the viewport, with no overlaps between them, with a route active and again with the GPS list open.
9. Cancel with the hint's ✕, then EXIT: the walking joystick comes back, nothing is held, and the page never scrolls.

Results:

| Suite | Result |
| --- | --- |
| `npm test` (unit, incl. drive router, one-way, pedestrian exclusion) | 87 / 87 pass |
| `touch-drive.spec` (mobile-390, mobile-360) | 2 / 2 pass |
| `touch.spec` (walking joystick, mobile-390 / 360) | 2 / 2 pass |
| `layout.spec` (desktop-1920, laptop-1366, mobile-390, mobile-360) | 4 / 4 pass |
| `driving`, `gps`, `opmode`, `ui`, `gameplay` (desktop-1920) | 25 / 26 in the batch run |
| `tsc --noEmit` | clean |

The one failure was the desktop test "walk to the car, E to get in, drive forward, brake, reverse…". Re-running it
on V8.5 passed 6 of 8 times; the two failures happened at different steps (speed after the 45-frame brake, then the
walk away). The same test passed 3 of 3 on the unmodified V8.4 code. That test holds keys for a counted number of
frames, but presses and releases them through asynchronous round trips, so the frames really driven vary. Desktop
does not create the touch layer, and none of the changed code runs on that path. I believe this is timing flake, but
I have not proven it. The full 27-minute suite was not run. Collision and chunk streaming are covered by the
`driving` and `gameplay` specs listed above.

## 4. Performance (Task 4): emulated, not a real phone

**No real Android phone or iPhone was available. All numbers are from emulation:** Edge on an Intel UHD laptop
GPU, 390×844 CSS px at DPR 3 with touch (`drive-bench.ts --mobile`, new option), Low graphics (render scale 1.25),
**4× CPU throttling**, and a GPS route to Lau Ya Keng active throughout. A real phone's GPU, thermal throttling and
browser will differ. Raw data: `docs/perf-v8.5-mobile.json`.

| Scenario | avg fps | median | p95 / p99 | frames > 50 ms / > 100 ms | peak JS heap | minimap + GPS / frame |
| --- | --- | --- | --- | --- | --- | --- |
| C block loop, cold | 23.1 | 41.1 ms | 83 / 115 ms | 624 / 36 | 182 MB | 1.25 ms |
| C block loop, warm | 22.6 | 43.8 ms | 80 / 100 ms | 683 / 18 | 104 MB | 1.14 ms |
| D 2 km at speed, cold | 34.3 | 23.9 ms | 66 / 92 ms | 384 / 19 | 100 MB | 0.68 ms |
| D 2 km at speed, warm | 33.1 | 26.5 ms | 66 / 94 ms | 350 / 23 | 92 MB | 0.73 ms |

- **Where the time goes:** rendering is 58–62 % of slow-frame time (16–25 ms per frame on average under the 4×
  throttle). Chunk building and the GPS are a small share. The dense V7 Jalan China section (loop C) is the
  heaviest.
- **Same config on V8.4 (paired cold run of C):** V8.4 20.1 fps, median 47.5 ms, 776 frames > 50 ms; V8.5
  20.2 fps, 46.5 ms, 750. The touch HUD adds no measurable cost.
- **Chunk loading while driving:** 0 frames driven on unbuilt ground, 0 off-road frames, never inside a building or
  water, top speed 93 km/h on D. V8.2's spread builds hold: the worst single build step was 63 ms, throttled.
- **Shader preparation (V8.1), pre-existing gap at Low:** on the cold run of loop C, 4–5 programs still compile
  late (`MeshStandardMaterial` variants near (205, −54) and `dun-gold`), 260–790 ms each under the throttle. The
  V8.4 build shows the same programs with the same stalls (350–740 ms vs 320–580 ms), so V8.5 did not cause them.
  V8.1's preparation evidently does not cover every program used by the Low preset. I left it alone, because the
  milestone said not to touch the renderer; it is the most visible remaining stutter on phones.
- **GPS responsiveness:** the first route, including the drive-graph decode, took 102 ms throttled. Re-plans took
  19–33 ms throttled (V8.4 unthrottled: 22–25 ms and 7–16 ms).
- **Touch latency:** 14–16 ms from the touch event to the first simulation frame that uses it, about one frame
  (measured in `touch-drive.spec`, unthrottled). Real devices add their own input pipeline delay on top.
- **GPU and memory:** GPU time cannot be measured from the page in this setup. JS heap peaked at 92–182 MB, the
  cold-start peak being highest.
- **Visibility and orientation:** a hidden page pauses the game (as before) and releases every control. An
  orientation change releases every control, and the landscape and portrait layouts are part of the sweep.

## 5. Known mobile limitations

- First drive through the old town at Low graphics: several 0.3–0.8 s shader-compile stalls (pre-existing, see
  section 4). This is the main candidate for a follow-up.
- **Not verified on real phones.** iOS Safari and Android Chrome behaviour, including multitouch limits, safe-area
  insets, and the browser bars changing the viewport height, is untested. Everything above is Chromium emulation.
- On mid-range phones, expect roughly 20–35 fps at Low graphics in the old town. The renderer was not changed in
  this milestone.
- The HUD panels use `backdrop-filter: blur`, which can cost GPU time on older phones. It was not changed, so the
  desktop look is preserved.
- Steering is a pad, not a tilt or wheel control. There is no haptic feedback.
- In landscape on short screens (≤ 390 px tall), the GPS list shows about 3 destinations at a time and scrolls.
- There is no forced landscape and no fullscreen request. The browser's own bars take space on phones.
- Very narrow landscape widths (< 760 px) were not tested. The GPS list gets tight there.
